### Behaviour change: self-service organizations get no limits, and the idle policy is opt-in per organization

- Organizations people create themselves (create-first-team, `POST /api/v1/tenants`) are no longer put on the Free plan. They start with no limits, like every other organization, and one person may create more than one. A self-hosted install with self-service sign-up on no longer caps new organizations at 5 seats and 500 assets on its own.
- The idle-organization policy (reminder, read-only, deletion due) used to apply to every Free organization. It now applies only where a platform administrator turned it on for that organization: `PUT /api/v1/admin/tenants/{tenantId}/idle/policy` `{enabled, reason}` (ops_admin+, reason required both ways, audited). It is off by default.
- Removed: `PUT /api/v1/admin/tenants/{tenantId}/idle/exemption` and the `exempt*` fields of `GET .../idle` (now `policy_enabled`, `policy_reason`, `policy_set_at`). Off is the default, so an exemption is no longer needed. The audit action `tenant.idle_exemption_changed` is now `tenant.idle_policy_changed`.
- Migration 002408 (`idle_policy_opt_in`) turns the policy off for every existing organization and returns every organization to `active`, so none stays read-only. Existing Free-plan rows are kept; organizations already on Free keep their limits until the plan model is replaced by per-organization limits.
- **Upgrade note:** stop the API while the migration runs (it drops the exemption columns). An operator who wants the idle policy for some organizations turns it on per organization after the upgrade.
