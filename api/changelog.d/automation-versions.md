### Behaviour change: automations have versions and start in simulate

- Publishing an automation (`POST /api/v1/workflows/{id}/publish`) stores its draft as an immutable version and makes it live. Live runs execute the published version, pinned when the run is created, so editing the draft never changes a live automation or a run already created. New automations start in `simulate`: their runs execute the draft and record what each action or notification would do, without doing it. `PUT /api/v1/workflows/{id}/mode {"mode":"simulate"}` switches back. `GET /api/v1/workflows/{id}/versions` lists the versions, and `.../versions/{versionId}/rollback` publishes an older version again as a new one.
- Editing an automation's draft no longer makes the editor its owner. Publishing or switching it on does, and live runs act as that person.
- `GET /api/v1/workflows/{id}` adds `mode`, `risk_class`, `draft_changed`, `published_version` and `pending_version`. Runs add `mode` and `version_id`.
- Migration 003350 (`automation_versions`) makes every automation that is switched on version 1, published by its owner, live, so it keeps acting. Automations that are off stay in simulate. Run steps no longer reference the draft's nodes, so replacing a draft keeps earlier runs' step history.
