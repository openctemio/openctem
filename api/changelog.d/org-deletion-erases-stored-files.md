### Security: deleting an organization deletes its stored files

- Deleting an organization (`DELETE /api/v1/tenants/{tenant}`) removed its rows but left every attachment and manual evidence file on disk (`STORAGE_LOCAL_PATH`), in the server bucket (`STORAGE_PROVIDER=s3|minio`) and in the organization's own bucket. The whole `{tenant id}/` namespace on each of these is now deleted before the rows (and once more after, for an upload that raced the delete). Other organizations' files are never touched: the namespace must be a canonical tenant id and the bucket prefix ends in `/`.
- **Behaviour change:** when a backend cannot be erased (storage down, or the organization's own bucket refuses its keys) the deletion is refused with 503 and nothing else changes; the owner retries. The refusal is audited as a failed `tenant.deleted` on the organization's log; a completed deletion's audit entry records `files_erased`.
- **Upgrade note:** files of organizations deleted before this release are not removed. They live under `<STORAGE_LOCAL_PATH>/<tenant id>/` (or the `<tenant id>/` prefix of the bucket); a directory whose name is not the id of an existing tenant can be deleted.
