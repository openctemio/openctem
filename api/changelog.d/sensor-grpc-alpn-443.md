### Added: sensor protocol v3 gRPC binding on port 443 in every setup (ALPN routing)

- The gateway image with the layer4 module routes a TLS connection whose ClientHello offers the ALPN id `openctem-sensor/3` to the API's mTLS listener (passthrough, PROXY protocol v2) on the platform's own port; every other connection is terminated as before. Works with an IP address, a single host name or no DNS at all; no extra port. `OPENCTEM_SENSOR_GATEWAY=alpn` (new, the default of `deploy/docker-compose.sensor-passthrough.yml`); `passthrough` now routes the ALPN id and the dedicated `SENSOR_PUBLIC_HOSTNAME` (SNI). RFC-059 T16 and §5.1 (deployment modes).
- Without `SENSOR_PUBLIC_HOST` the API derives the gRPC endpoint from the platform URL's own host and port (an IP address too), instead of `sensors.<host>`. The self-probe offers the sensor ALPN id; a second probe without it decides whether hello names the endpoint as `grpc_endpoint` (any client) or only as the new `grpc_alpn_endpoint` (clients that offer the id: sdk-go with `client.SensorALPN`). `GET /api/v1/sensors/transport` reports `requires_alpn`; probe metric result `ok_alpn`.
- Behind the stock gateway nothing changes: the probe meets the gateway's certificate and sensors keep the HTTPS binding (logged at info, not as a warning, when the endpoint is derived).
- **Upgrade note:** a deployment that relied on the derived `sensors.<host>` name sets `SENSOR_PUBLIC_HOST=sensors.<host>:443` explicitly (the compose override already does with `passthrough`). Behind the layer4 gateway set `SENSOR_MTLS_TRUSTED_PROXIES` to the gateway's address (the override does).
