### Fixed: a new collector sensor gets the collector grant, and its refused reports say why

- A sensor created with type `collector` (create API, or a pairing approval with no profile chosen) now gets the `collector` grant profile (collect and connector_sync jobs, passive tier, no target network, push ingest on) instead of `internal-network-scanner`, which had push ingest off and refused every report. Migration 002075 changes the insert trigger only: existing sensors keep their grant.
- Trust is still never automatic: a new collector stays at trust level New and its reports are refused until an administrator promotes it. The install flow offers **Trust this collector to push asset reports** (off by default; `"trusted": true` on `POST /api/v1/sensors`, collector only). It needs `sensors:grant:widen`, is checked before the sensor is created, and is audited and notified like any promotion.
- `PUSH_INGEST_NOT_GRANTED` (protocol v2 item error `push_ingest_not_granted`) now names what is missing, the grant or trust, in its message and detail; the sensor timeline event and `sensor.push_refused_grant` audit entry carry `missing`. The sensor's Grant section explains a refused collector and links the fix.
- **Upgrade note:** a collector created before this release on `internal-network-scanner` keeps being refused. Change its profile to `collector` and promote it to Trusted on its Grant.
