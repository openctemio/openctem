### Security: a second super admin approves the console's most dangerous actions

- Making or removing a super admin, turning off the security-key requirement, removing or relaxing the administrators' identity provider, opening sign-up and re-signing an organization's audit chain now need another super admin's approval when one exists. The protected route answers `428 SECOND_APPROVAL_REQUIRED`; the console asks for the approval (reason, step-up), another super admin approves under Security > Approvals (fresh step-up), and the requester repeats the action within 24 hours. An approval is bound to its requester, action and exact target, works once and expires; nobody approves their own request (also a table constraint); break-glass accounts never approve and do not count as a second super admin. Every step is audited critical and e-mailed to the administrators.
- With one named super admin the actions run on that admin's step-up alone, audited critical (`approval.single_admin`) and announced; the Approvals page explains how to add a second super admin.
- Migration `002914_admin_approvals` adds the `admin_approvals` table (new, empty; safe on a populated database).
- **Upgrade note:** installations that run the console with its own database role (`DB_ADMIN_USER`) re-run the role script (`deploy/postgres/least-privilege-roles.sql` with `admin_user`, or `db-grants`) so the console role gets `admin_approvals` and the app role loses it. Installations with two or more named super admins should expect the approval step on these actions from this release.
