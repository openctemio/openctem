### Fixed: concurrent re-runs of one repository no longer deadlock or lose sightings

- When many uploads reported the same findings at once (CI re-runs, matrix jobs), the batched writes locked rows in an unpredictable order and deadlocked. The sighting-only fallback then deadlocked too, and sightings were lost: in a 20-way load test every upload ended with errors and one round recorded 3,000 of 10,000 sightings. Every batched write now locks its rows in one order (assets by name, new findings by fingerprint, existing findings by id). Enrichment reads and writes the stored rows under that lock in one transaction. A deadlock or serialization failure that still happens is retried with bounded, jittered back-off, and the per-row fallback is no longer used for it. A finding whose enrichment already landed is no longer counted a second time by the fallback.
