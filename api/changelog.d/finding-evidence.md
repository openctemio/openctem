### Security: finding evidence is masked by default; revealing a value is a stepped-up, audited action

- A finding now shows the proof its tool attached: the request that was sent, the response that came back with the matched part highlighted, extracted values and a reproduction curl (finding page, Evidence tab, "Tool evidence"). The nuclei sensor already sends this; until now it was dropped.
- Secret values in that proof (Authorization and other auth headers, cookies, tokens in URLs and bodies, credential shapes) are masked as `«secret:kind#n»` by the platform, whatever the tool marked, and stored AES-256-GCM encrypted apart, bound to the tenant and the item.
- Revealing a value needs the new permission `findings:evidence:reveal` (owner and admin by default; assignable to custom roles), the finding in the caller's data scope, a recent sign-in (step-up; API keys cannot reveal) and stays under a per-user rate limit. Every reveal is written to the audit log (`finding.evidence_revealed`, never the value) before it returns and appears on the finding's timeline; the web masks the value again after 60 seconds.
- Encrypted values are kept 30 days by default (`PUT /api/v1/organization/settings/evidence` `secret_retention_days`, 1–365), the masked evidence 365 days; finding and tenant deletion remove both. Evidence never appears in finding lists, exports, notifications, tickets or AI-triage prompts.
- Migration 001210 adds `finding_evidence`, `finding_evidence_secrets`, the permission and the `evidence_revealed` activity type.
- **Upgrade note:** `cmd/rekey` re-encrypts `finding_evidence_secrets.ciphertext` with the other key-protected values.
