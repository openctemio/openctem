# Database Migrations

## Overview

Migration files live in `migrations/` and are applied by `openctem-migrate`
(`cmd/openctem-migrate`, [RFC-130](../rfcs/RFC-130-migration-applied-set.md)).
It records every applied version and applies every migration a database has
not applied yet, lowest version first. A version only has to be unique: a
migration merged after a higher-numbered one is applied on the next run, not
skipped.

## Prerequisites

Nothing to install: `make migrate-up` (and `scripts/migrate.sh`) run this
tree's runner with `go run`. To build it once:

```bash
GOWORK=off go build -o bin/openctem-migrate ./cmd/openctem-migrate
```

## File Structure

```
migrations/
├── NNNNNN_baseline.up.sql     # the schema + built-in rows of every migration up to NNNNNN
├── NNNNNN_baseline.down.sql   # refuses: the baseline is not reverted
├── NNNNNN_*.up.sql / .down.sql          # legacy sequential versions (no new ones)
├── YYYYMMDDHHMMSS_*.up.sql / .down.sql  # every new change: a UTC timestamp version
└── seed/                      # optional data (seed_required.sql, seed_test.sql, ...)
```

A fresh database applies the baseline and then every migration above it, in
version order. Migrations are expand-contract safe
(`scripts/check-migrations.sh`) and have a working down migration.

### Versions only have to be unique

`schema_migrations_applied` holds one row per applied migration, and `up`
runs every shipped migration missing from it. So:

- a migration written on Monday and merged on Friday, after migrations written
  on Tuesday, is applied on every database the next time it migrates: after
  them on a running install, before them on a fresh one. CI proves that both
  orders give the same schema (`.github/scripts/migration-order-check.sh` in
  "Migrations (PostgreSQL 18)"); when they do not, the later-merged migration
  depends on the others and needs a version above them
  (`make -C api migration-renumber` while it is not merged);
- **a merged migration never changes.** Databases that applied it never run
  it again: an edit, a removal or a rename would only reach fresh installs.
  Fix a merged migration with a new one. The "Migration Versions" check
  refuses a changed, removed or renamed merged up file (down files may be
  fixed; a baseline that replaces the chain is the exception).
- `schema_migrations` keeps one row: a *fence* version that no file has while
  clean, or the failed migration's version while dirty. An older migrations
  image refuses the fence, so it can never skip a migration on a database this
  runner migrated.

### Picking a version

Nobody picks a version by hand.

- `make -C api migration-new name=<snake_name>` creates
  `migrations/<UTC now>_<snake_name>.{up,down}.sql` (one second later while
  that version exists). It needs no network: timestamps of parallel branches
  do not collide.
- `make -C api migration-renumber` gives this branch's added migrations new
  timestamp versions when one is also used by `develop` or an open pull
  request, or still has a legacy sequential number; the migrations after it
  move too, in order. It rewrites references to the old file names outside
  `api/migrations/` and stages the renames.
- Pull request CI gives a clashing migration a new version in its runner only
  (`.github/scripts/pr-migration-renumber.sh`), so a duplicate never fails a
  pull request's tests; in the merge queue a duplicate fails. Tests find
  migrations by name (`testdb.MigrationVersion`), so a new version never
  touches a test.
- Legacy sequential numbers (six digits) are still accepted, with a warning,
  while older pull requests land, but only above the base's highest legacy
  number: when the runner first takes over a database the earlier tool
  (golang-migrate) migrated, it records every legacy-numbered file up to that
  tool's version as applied.

### Indexes

Every index is maintained on every write to its table, so no table may carry
two indexes with the same keys, operator classes, sort options, predicate and
expressions (`TestNoDuplicateIndexes_DB` fails on one). A unique index also
serves lookups with its columns in the other order, so a second unique index
on the same two columns swapped is a duplicate too; the test cannot see that
case, so check for it in review.

- Create and drop an index on an existing table with `CONCURRENTLY`, as the
  only statement in its file (it cannot run inside a transaction block).
  A partitioned parent cannot use `CONCURRENTLY`: set `lock_timeout` and keep
  the statement short.
- Before dropping a unique index, check `pg_constraint.conindid`: a foreign
  key bound to it blocks the drop, and PostgreSQL cannot re-point it.
  `003191_drop_dup_unique_indexes` shows the pattern (drop the dependent keys,
  drop the index, re-add the keys unchanged and validate them).

## Migration baseline

[RFC-053](../rfcs/RFC-053-migration-baseline.md). The chain of earlier
migrations is replaced by one file, `NNNNNN_baseline.up.sql`, generated by
`scripts/squash-migrations.sh` with `pg_dump` from a database that ran the
whole chain. It carries the schema (tables, indexes, constraints, functions,
triggers, comments, the RLS policies in shadow mode) and the built-in rows
(permissions catalogue, system roles, modules, tools, ...), without owners or
grants: objects belong to the migrator that applies it, and
`deploy/postgres/least-privilege-roles.sql` grants the app role as before.

- **Do not edit the baseline.** Change the schema with a new migration above it.
- **Fresh database**: the runner applies the baseline, then the rest. The
  baseline refuses to run on a database that already has the schema.
- **Database that has the baseline applied** (or, migrated by the earlier
  tool, is at its version or later): never runs the baseline.
- **Database older than the baseline**: `openctem-migrate` refuses it,
  changing nothing, and says what to do (so does the API's startup check):
  back up, deploy the last release before the baseline (git tag
  `pre-baseline-NNNNNN`, which still has every old migration), run its
  migrations, then deploy the new release.
- **History**: the old migration files, their tests and their runbooks are in
  the tree at tag `pre-baseline-NNNNNN` (`git show pre-baseline-NNNNNN:api/migrations/<file>`).

### Squashing again

When the chain has grown long again, squash at a release boundary:

```bash
# from a branch off develop; REF is the commit whose migrations are squashed
scripts/squash-migrations.sh origin/develop   # builds openctem-migrate, or MIGRATE=/path/to/it
```

The script applies REF's chain to a throwaway PostgreSQL 17, writes the new
baseline at REF's highest version, removes the files it replaces, and then
proves the result: chain vs baseline, as the superuser and as the
least-privilege migrator, schema byte-identical (owners and grants included)
and data identical once run-time values (`now()`, random UUIDs) are masked.
It exits non-zero on any difference. A table that should not survive the
squash is left out with `EXCLUDE_TABLES`, and a migration above the baseline
must drop it on existing databases (the proof fails otherwise).


### Seed Data Philosophy

Seed data is split into two categories:

1. **Required data** (`seed_required.sql`): Essential data the system needs to function
   - Currently empty - OpenCTEM creates all data dynamically
   - Add system configurations, default roles, etc. if needed

2. **Test data** (`seed_test.sql`): Development/testing data
   - Sample users, tenants, assets, projects, vulnerabilities, findings
   - **Never run in production!**

```bash
make migrate-up                 # apply every migration the database has not applied
make migrate-down               # roll back the most recently applied migration
make migrate-status             # highest applied version and the pending migrations
```

-database "postgres://user@host:5432/db?sslmode=..." up|down N|force V|version|status`,

## Schema Overview

The schema is the baseline plus the migrations above it; read it from a
migrated database (`\d+` in psql) or from the baseline file. Row-level
security policies exist on the tenant tables but RLS is not enabled (shadow
mode); tenant isolation is enforced in the queries (`WHERE tenant_id = $n`).


## Writing Migrations

### PostgreSQL Functions Convention

When creating database functions in migrations:

1. **Document in `docs/architecture/database-notes.md`** - Add function signature, description, and usage examples
2. **Use consistent naming** - `verb_noun_noun` pattern (e.g., `recover_stuck_jobs`, `renew_sensor_lease`)
3. **Return meaningful types** - Use `RETURNS TABLE` for complex results with multiple fields
4. **Include comments in SQL** - Use `COMMENT ON FUNCTION` for function documentation
5. **Match Go interface** - Ensure function signature matches the Go repository method that calls it

**Example** (illustrative):
```sql
-- Function with proper documentation
CREATE OR REPLACE FUNCTION recover_stuck_jobs(
    p_stuck_threshold_minutes INT DEFAULT 30
) RETURNS INT AS $$
DECLARE
    recovered_count INT;
BEGIN
    -- ... implementation
    RETURN recovered_count;
END;
$$ LANGUAGE plpgsql;

COMMENT ON FUNCTION recover_stuck_jobs IS
    'Return stuck jobs to the queue when a sensor goes offline (max 3 retries)';
```

**Go usage:**
```go
// Matches the DB function signature
func (r *CommandRepository) RecoverStuckJobs(ctx context.Context, thresholdMinutes int) (int64, error) {
    query := `SELECT recover_stuck_platform_jobs($1)`
    var count int64
    err := r.db.QueryRowContext(ctx, query, thresholdMinutes).Scan(&count)
    return count, err
}
```

### Best Practices

1. **Make statements idempotent**
```sql
-- Good: Won't fail if run twice
CREATE TABLE IF NOT EXISTS users (...);
CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);

-- For constraints, use DO blocks
DO $$ BEGIN
    ALTER TABLE users ADD CONSTRAINT users_email_unique UNIQUE (email);
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
```

2. **Always write both UP and DOWN**
```sql
-- Down should completely reverse UP
DROP TABLE IF EXISTS users;
DROP INDEX IF EXISTS idx_users_email;
```

3. **Test rollbacks**
```bash
make migrate-up
make migrate-down
make migrate-up    # Should work again
```

4. **Never modify existing migrations after deployment**
   - Create new migration instead
   - Old migrations are backed up in `_backup/` for reference

5. **Pick the ON DELETE action for every FK to `tenants` and `users`**

   Deleting an organization (`DELETE /api/v1/tenants/{tenant}`) or a user is a
   plain `DELETE`; a `NO ACTION`/`RESTRICT` key makes it fail for every tenant
   or user that has such a row.

   | Reference | Action |
   |-----------|--------|
   | `tenant_id` of a row the tenant owns | `ON DELETE CASCADE` |
   | a user who *did* something (`created_by`, `assigned_by`, `approved_by`, `actor_id`, ...) | nullable column, `ON DELETE SET NULL` |
   | a row that *is* the user's (`sessions`, `user_roles`, `tenant_members`, ...) | `ON DELETE CASCADE` |
   | an audit/history row (`audit_logs`, `asset_state_history`, `suppression_rule_audit`, ...) | `ON DELETE SET NULL`, never `CASCADE` from `users` |

   `TestDeleteFKPolicy` (`internal/infra/postgres/tenant_user_delete_db_test.go`)
   reads every such key from `pg_constraint` and fails on a blocking one unless
   it is in `blockingFKAllowlist` with a reason.
   `TestDeleteTenantAndUser_EverySchemaTable` seeds a row in every table with a
   `tenant_id` column and checks both deletes; a new table it cannot seed fails
   the test until `seedOverrides` learns its constraints.

   `asset_state_history` is immutable by trigger. Since migration 000242 its
   triggers admit only the referential actions: the `changed_by` SET NULL when
   the user row is gone, and the delete of a recent row once its asset or
   tenant is gone. Direct `UPDATE`/`DELETE` of a recent row still fails.

## Troubleshooting

### Dirty Database State

When a migration fails, its file is rolled back (one implicit transaction
unless the file manages its own) and the database is marked dirty at its
version: every command but `force` refuses, and so does the API.

```bash
make migrate-status
# Output: 20261027101500 (dirty) ...

# The migration completed, or you finished it by hand: record it
make migrate-force version=20261027101500

# Or undo its partial changes, then only clear the flag so up retries it
make migrate-force version=-1

make migrate-up
```

### Other refusals

`openctem-migrate` changes nothing and says what to do when:

- the database is older than the migration baseline (see above);
- a newer release migrated it (an applied version above every shipped one):
  run the newer release's migrations, or restore the pre-upgrade backup;
- another migration tool rewrote `schema_migrations` after the runner took the
  database over: check what that tool applied, record each applied migration
  with `force`, then `up`;
- the earlier tool (golang-migrate) migrated the database past a timestamp
  version: it may have skipped some, so check each listed version in the
  schema, record the applied ones with `force`, then `up` applies the rest.

### Complete Reset (Development)

```bash
# Nuclear option: reset everything
make db-fresh
```

### Check Schema Migrations Table

```bash
make docker-psql
# Then in psql:
SELECT version, name, applied_at FROM schema_migrations_applied ORDER BY applied_at DESC LIMIT 20;
SELECT * FROM schema_migrations;   -- the fence (9223372036854775807, f), or (version, t) while dirty
```

### Test User Accounts

The seed files do not create users or passwords. Create them the way a first
install does, with `bootstrap-admin`: a platform administrator, and the first
organization with you as its owner:

```bash
SMTP_BASE_URL=http://localhost:3000 GOWORK=off go run ./cmd/bootstrap-admin \
  -email admin@example.com -no-backup \
  -org-name "Dev" -org-slug dev -org-owner-email you@example.com
```

Open the printed one-time `/set-password#token=...` link to choose the owner's
password, then sign in at `/login`. The administrator signs in with the printed
temporary password and opens the platform console at the root of its own
site (`npm run dev:console` in `web/`, port 3001, locally).

Never commit password hashes to docs or seeds, even for test accounts.

## CI/CD Integration

### GitHub Actions

CI builds the runner and applies every migration
(`openctem-migrate -path migrations -database "$DATABASE_URL" up`), and on a
change to `api/migrations` proves order independence
(`.github/scripts/migration-order-check.sh`). See
[ci-cd.md](ci-cd.md).

### Production Deployment

```bash
# 1. Apply migrations (the migrations image, or)
make migrate-up

# 2. (Optional) Seed required data
make docker-seed-required

# 3. Start application
./server
```

**Never run `docker-seed-test` in production!**
