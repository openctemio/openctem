### Added: held findings when the target throttled or blocked the scan

- A finding gets a verification state: `unchecked` (default, every existing finding), `held`, `verified` or `not_reproduced`, with the codes behind a hold (`edge_block_page`, `throttled_response`, `soft_404`, `target_throttled`, `timing_based`, `oob_weak`). The finding API returns `verification_state` and `hold_reasons`; the findings list and the query language filter on `verification_state` (for example `verification_state=held`).
- When a scan command's result names a host as throttled, blocked, edge protected, at the rate floor or answering every path alike (coverage gaps), the findings that command's reports sighted first on that host are held with `target_throttled`: when the report is ingested if the result is already in, otherwise when the command's coverage is evaluated. A held sighting never downgrades a finding that was already there or was verified; a clean sighting releases a held finding.
- A held finding is kept and listed, but stays out of asset risk counts and rollups, business unit and asset group counts, dashboard open and overdue counts, KEV critical counts, emerging-threat alerts, SLA breach and at-risk escalation, new-finding events (notifications, automation rules), priority-escalation notices, and ticket creation (an automatic Jira ticket becomes a policy hold that is released once the finding is checked; an automation `create_ticket` step is skipped with reason `finding_held`).
- One notice per hold, `finding_held_critical` (default on for new integrations), says how many critical findings were held.
- Migrations 20261114071207 (`findings.verification_state`, `findings.hold_reasons`, constant defaults, CHECKs added NOT VALID then validated: no table rewrite) and 20261114071208 (partial index `idx_findings_tenant_held`, built concurrently). Schema only, no data changes.
