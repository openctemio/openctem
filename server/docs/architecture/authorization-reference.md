# Authorization reference (generated)

The authorization reference describes who can do what in OpenCTEM. It is
generated from the source by `cmd/gen-authz-docs` (package
`internal/authzdoc`) and is never written by hand. The rules it describes are
in [authorization-matrix.md](authorization-matrix.md); this page explains the
generator.

## What it reads

| Input | Source |
|---|---|
| Permission catalog | `permission.AllPermissions()`; names and descriptions from the seed migrations; admin-only flags from `permission.IsAdminOnly` |
| Built-in roles | `permission.SystemRoles()` (the seed is held equal to it by `TestSystemRolePermissions_MatchSeed`) |
| Role templates | `permission.RoleTemplates()` |
| Route gates | the route source under `internal/infra/http/routes` (AST): `Require`, `RequireAll`, `RequireAny`, tenant-permission wrappers, team-role gates, `RequireModule` (including module gates passed as arguments), `requireStepUp()`, and other named gates (campaign role, platform administrator, permission-or-self) |
| Why a route has no gate | `routeAuthzAllowlist` and `allowlistPrefixes` in `tests/unit/route_authz_coverage_test.go` |
| Data scope per route | `dataSurfaceRegistry` in `tests/unit/route_scope_classification_test.go` |
| Features | `authzdoc.Features`: each route-registering function belongs to one feature |
| Personas and recommended teams | `authzdoc.Personas`, `authzdoc.TeamPatterns` |

## What it writes

- `web/src/config/authz-matrix.json`: the whole reference for the web console. It is used by the role editor's matrix and by the explanation of a refused action. It is generated by `make contract` (and so by `make generate` at the repository root, and in CI), and is not committed, like the other contract files.
- Markdown pages, with `make authz-docs DIR=<dir>` (add `FRONT_MATTER=1` for the documentation site):
  - `index.md`
  - `roles-matrix.md` (every permission against every built-in role and template)
  - `personas.md` (persona to roles, team, data scope and access)
  - `features/<feature>.md` (per route: the permissions required, the data-scope class, step-up, and the roles and templates that pass)

  The documentation site regenerates these pages from each release.

## Refused requests name what is missing

A permission or team-role gate that refuses a request still answers
`403 FORBIDDEN` with the same message, and now adds `details`:

```json
{"code": "FORBIDDEN", "message": "Insufficient permissions",
 "details": {"missing_permissions": ["findings:verify"]}}
```

`details.any_of` lists the alternatives of a `RequireAny` gate, and
`details.required_role` names the team role (`admin`, `owner`, `member`) a
role gate needs. The permission catalog and role names are visible to anyone
who can open the role editor, so naming them discloses nothing. A data-scope
refusal never comes through here: an asset outside the caller's scope still
answers 404. A disabled module answers `403 MODULE_NOT_ENABLED`.

## CI guards

- `TestEveryRouteIsClassified` (`internal/authzdoc`) fails in these cases:
  - a route belongs to no feature;
  - a feature lists a register function that registers nothing;
  - a route has neither a gate nor an allowlist reason;
  - a route has no data-scope class;
  - not even the owner passes a route's gate.
- `TestPersonasAndTeamsAreConsistent` fails when a persona or team names an unknown role or team.
- The existing guards keep their jobs:
  - every route is gated or allowlisted (`route_authz_coverage_test.go`);
  - every route has a data-scope class (`route_scope_classification_test.go`);
  - the catalog matches the seed (`permission_catalog_sync_test.go`).

The outputs are not committed, so they cannot go stale. CI generates them on
every run.
